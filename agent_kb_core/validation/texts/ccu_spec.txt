ECU 对网络的通信需求，以如下表格形式体现在 SDRS 中。该表格可能存在于 SDRS 的不同章

每个 ECU 可以承接多个功能场景，每个功能场景需要保持工作的 CAN/CANFD 网段和 ECU 可
以不同。为了减少不同功能场景下不必要的节点被唤醒，从而提高电池电量使用时间，因此小
米采用如下网络管理和设计方式：
同一条 CAN/CANFD 网段上所有 ECU，应支持通过 CAN NM 报文实现同步唤醒和休眠（部分
不实施 CAN NM 的智能配电节点除外）
以 CAN NM 报文中不同 User Data Bit 表示不同的网段组合
各功能场景都会被 Map 到 1 个特定的 User Data Bit
注：各功能场景和 User Data Bit 的映射关系，User Data Bit 和网段组合的映射关系，以及各功
能场景的编号，小米都会随 SDB 一起释放给供应商。

考虑到 CAN NM 报文中 User Data Bit 数量有限，而且整车涉及的功能场景数量庞大，因此存
在多个功能场景被 Map 到同 1 个 User Data Bit 的情况。
当多个功能场景被 Map 到同 1 个 User Data Bit 时，且其中任一个功能场景需要唤醒/保持唤醒
User Data Bit 对应的网段组合，那么对应的网段都应保持唤醒。只有当所有功能场景的休眠条
件都满足时，对应的网段才能休眠。

从 ECU 视角，功能场景、User Data Bit 和 ECU 所连 Channel 的关系如下图示例，小米会基于
整车所有功能场景，统一分配功能场景、通道和 User Data Bit 的 Map 关系，并随 SDB 释放给
供应商。

18/148

ECU 通过发出 CAN NM 报文中 User Data Bit 置 1，表示 ECU 中相应功能场景的唤醒/保持唤醒
条件满足，此时 ECU 和网关节点需要主动唤醒 User Data Bit 对应的网段组合。
ECU 通过发出 CAN NM 报文中 User Data Bit 置 0，表示该 User Data Bit 对应的全部功能场景
的唤醒/保持唤醒条件都不满足。

如果 ECU 承载所有功能场景的唤醒/保持唤醒条件都不满足后，意味着 ECU 对外部网络和节点
没有信号需求，此时 ECU 应执行 Network Released，之后 ECU 停发 CAN NM 报文。这意味
着，如果 ECU 因为本地唤醒条件满足而唤醒网络，ECU 在发出的 CAN NM 报文中一定有至少
1 个 User Data Bit 置 1（诊断保持网络场景不需要置位任何 User Data Bit）。（T10 规范中定
义 Bit16 表示 ECU 当前是否处于 Repeat Message State，本文提到的 User Data Bit 不包括
Bit16）。

1.桩端结束并切换 S1 时，CCU 检测到 6V PWM 信号变成常电平，CCU
应能按规定时间停机并实时更新 CP 信号。

VCUOBCModReq=Charging 或 Heating 变成 VCUOBCModReq=Standby
（正常充电结束指令）。

1.充电过程中，CCU 在检测到 S3 由连接变为半连接后，应能在 100ms

2.充电过程中，CP 信号中断，CCU 在 3s 内停机（GB/T 18487.2015，
A3.10.3），CCU 发送 OBCCpSts=NOK。
