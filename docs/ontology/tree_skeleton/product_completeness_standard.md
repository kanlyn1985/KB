# 产品完备性标准（Product Completeness Standard）v0.4

> 领域：`obc_dcdc`（OBC/DCDC）
> 被测对象：`docs/ontology/tree_skeleton/skeleton_v0.4.json`（**骨架是被测对象，不是标准**）
> 判定标准：三条独立公理（来源 = 领域知识 + 行业标准 + 系统工程 V 模型）
> 检查器：`agent_kb_core/validation/check_product_completeness.py`
> 清单数据：`docs/ontology/tree_skeleton/product_completeness_checklist.json`

## 0. 为什么标准必须「独立」

如果标准是从骨架现状推导出来的（比如「ID 前缀等于层」「R→F 关联存在」），测试就变成
「骨架是否符合它自己」——永远能自圆其说，测不出真实缺口，没有测试意义。

因此本标准的判定依据**完全不来自骨架**，而来自三个独立来源：

1. **OBC/DCDC 领域知识** —— 产品是什么、能做什么、由什么组成、怎么做、怎么验。
2. **行业标准** —— GB/T 40432 / GB/T 18487 / ISO 26262 / ISO 14229 / ISO 15118 / ASPICE。
3. **系统工程 V 模型** —— 需求 → 设计 → 实现 → 验证 → 生产 的可追溯性。

骨架是被测对象，标准是固定的「尺子」。换任何一个骨架版本，尺子不变。

## 1. 目标（一句话）

**「整个骨架的所有节点合起来，能把 OBC/DCDC 产品做出来。」**

## 2. 三条公理

### 公理1 覆盖（Coverage）—— 必备要素都命名了
完整产品必须覆盖一套固定「必备要素清单」（86 条，分 9 层：需求 / 功能 / 逻辑软件 /
物理硬件 / 制造工艺 / 验证测试 / 方法 / 质量经验 / 实例）。
判定：每条要素在骨架中是否有对应节点（按名称/别名关键词命中）。

### 公理2 深度（Depth）—— 每个节点有落地内容
「命名了」不等于「做得出来」。每个节点必须有足够落地内容（文档数 / 单元数达到阈值），
才能支撑后续真正执行。
判定：按 210 个节点逐个统计 —— 充分 / 薄（doc<5 或 unit<10）/ 无卡。

### 公理3 连接（Connectivity）—— 要素连成链
要素之间必须能连成可追溯链：需求 R → 功能 F → 逻辑 L → 物理 P → 工艺/验证 G。
一个需求要能一路走到「某个物理零件 + 造它的工艺 + 验它的测试」，才算可追溯。
判定：逐层统计跨层关联覆盖率 + 关联的证据覆盖率。

## 3. 当前基线（2026-08-22）

| 公理 | 结果 | 判定 |
|------|------|------|
| 1 覆盖 | 86/86 = 100% | 概念齐全 |
| 2 深度 | 201/210 = 95.7% | 8 薄 + 1 无卡（F-DCDC） |
| 3 连接 | ≈ 2% | **核心缺口** |

公理3 明细：

| 链 | 现状 |
|----|------|
| R→F 需求被功能满足 | 0/11 |
| F→L 功能被逻辑实现 | 0/11 |
| L→P 逻辑分配到物理 | 6/17 |
| P→G 物理被工艺/验证覆盖 | 0/59 |
| 关联证据覆盖 | 0/7 |

## 4. 结论与补全顺序

骨架「概念上齐全（100%）、深度基本够（95.7%），但跨层链几乎没连（≈2%）」——
即 210 个节点各立门户，还没连成「能做出产品」的链条。与目标的差距集中在**公理3**。

补全顺序：

1. **补连接（最优先）**：R→F 11 条 → F→L 11 条 → L→P 补 11 条 → P→G 59 条，目标 R 全链路→P 达 100%。
2. **补证据**：给每条关联填 `evidence_refs`。
3. **补深度**：给 `F-DCDC` 生成卡片；补强 8 个薄节点。
4. **关系类型具名化**：satisfies / realized_by / allocate / produced_by / verified_by。
