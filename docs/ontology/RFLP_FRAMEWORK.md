# RFLP 产品构成框架（讨论稿）

> 状态：讨论稿 v0.1（2026-08-06）
> ✅ 已验证：项目计划模板 100% 活动可落入本框架（RFLP 四层 + 过程维度）
> ❓ 未定稿：层间关系清单/完整性规则/实现机制的最终定义

## 1. 定位

产品不能用一个平面表达，用 **RFLP 四层（产品构成）+ 过程维度（怎么来）** 完整描述：

```
R 需求层   产品为什么存在？    → 要满足什么（客户要求/标准法规）
F 功能层   产品做什么？        → 功能上要具备什么能力（不关心实现）
L 逻辑层   产品怎么组织？      → 逻辑上如何分工协作（不绑定硬件/软件）
P 物理层   产品用什么实现？    → 真实的硬件/软件/数据/接口
──────────────────────────────────────────────
过程维度   产品怎么来？        → 开发/验证/生产/管理过程（作用于各层节点）
```

## 2. 四层内容（OBC 例）

| 层 | 内容 | OBC 例子 |
|---|---|---|
| R | 客户需求/标准法规/系统需求→软硬件需求（ASIL/来源/验证方法） | "输入电压 85~265VAC"（MI-MD-13065） |
| F | 功能分解树/用例/场景（不关心实现） | 充电功能→{AC-DC 变换、电压调节、电流限制、通信} |
| L | 逻辑组件/数据流/状态机（抽象，不指定实现） | 充电控制逻辑块、故障管理逻辑块、通信逻辑块 |
| P | 硬件树/软件树（AUTOSAR 式）/标定数据树/接口树 | PFC 电路、充电控制 ASW、降额曲线标定表、CAN 接口 |

性能参数（效率/纹波/精度）= **跨层约束**（SysML 参数图）：挂在功能-物理映射两端，不归属某一层。

## 3. 层间关系

| 关系 | 方向 | 语义 | 例子 |
|---|---|---|---|
| refined_by | R→R | 需求逐级细化 | 客户需求→系统需求→软/硬件需求 |
| satisfy | R→F | 需求被功能满足 | "纹波≤5%" satisfy "纹波抑制功能" |
| allocate | F→L | 功能分配给逻辑组件 | "纹波抑制" allocate "纹波抑制逻辑块" |
| allocate | L→P | 逻辑分配给物理实现 | 逻辑块 allocate 软件 ASW / 硬件滤波电路 |
| mapped_to | P软→P硬 | 软件部署到硬件 | ASW 模块 mapped_to MCU |
| verify | R/F/L/P→验证活动 | 各层被验证 | "纹波≤5%" verify 电气性能测试 |
| trace | 任意↔任意 | 全链可追溯（可推导/可显式存） | 需求→功能→逻辑→物理→测试 |

层内关系：R 层内 refined_by（需求分解树）；F 层内功能分解；L 层内逻辑分解；P 层内 part_of（硬件树/软件树/BOM）。

## 4. 关系数据模型

```
关系边 = {
  relation_type: "satisfy",         ← 注册表类型
  category: "referential",
  source: {node_id, layer: "R"},
  target: {node_id, layer: "F"},
  inverse: "satisfied_by",          ← 逆关系（双向遍历）
  condition: "充电模式",             ← 可选：关系成立条件
  evidence_refs: ["evd_xxx"],       ← 证据（evidence-first）
  source_req: "MI-MD-13100",        ← 由哪条需求建立（可审计）
  confidence: 1.0,
  project_scope: "曼岛"
}
```

## 5. 实现机制

```
① Schema：关系注册表（relation_types 升级）
   {name, category, direction, source_types允许[], target_types允许[], inverse}
   ——白名单校验在代码侧强制（R 不能 allocate P）
② 数据：SQLite 边表（graph_edges 升级），支持按类型/层/项目查询 + BFS 遍历
③ 查询：穿透查询——任意层节点沿边到达其他层关联节点（"一层查全链"）
```

## 6. 完整性规则（树校验）

```
R1 每个 F 功能必须被 ≥1 条 R 需求 satisfy     无需求的功能 = 无来源
R2 每个 L 逻辑必须被 ≥1 条 F 功能 allocate    无功能的逻辑 = 空转
R3 每个 P 物理节点必须被 ≥1 条 L 逻辑 allocate 无逻辑的物理 = 孤儿
R4 每个 R 需求必须有 verify 边到验证活动       未验证的需求 = 未闭环
R5 关系两端类型必须过注册表白名单             防错连
R6 每个节点至少有 1 条关系边（除根）           防孤立节点
```

## 7. 项目计划活动映射（验证记录）

| RFLP 层/过程 | 模板中的活动 |
|---|---|
| R | 客户需求收集、FSR/TSR、软件需求分析（SWRD） |
| F | 产品系统设计、HIS 设计、故障/诊断列表（**隐式**，融在系统设计里） |
| L | 软件架构 HLD、详细设计 LLD、TSC/SAD |
| P | 电子/磁件/结构详细设计、软件代码（ASW/BOOT/AUTOSAR）、BOM |
| 验证过程 | 电子/EMC/结构样机测试、软件层级验证、系统功能、DV/PV |
| 生产过程 | 过程开发（PCBA/组装/生产测试）、试制、PPAP、SOP |
| 管理过程 | 项目/质量/供应链活动（支撑性，不属于 RFLP 四层） |
