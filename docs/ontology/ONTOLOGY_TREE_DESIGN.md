## 1. 定位与目标 ❓讨论中

本体树是 agent_kb_core 的领域知识骨架，回答两个问题：

1. **OBC/DCDC 本体及子本体里都有什么内容**（可枚举的概念树）
2. **这些内容有什么属性**（值类型/单位/限值/条件），属性值随项目/平台变化

讨论中提出的候选原则（**未定稿**）：

- **自顶向下构建**：根本体（OBC/DCDC 是新能源汽车行业产品）→ 行业知识（标准体系/产品架构/项目计划模板）→ V1.0 树 → **文档落位验证** → 落不进的**增枝**（不是从文档自底向上提取）
- **本体相同、属性随项目变**：树（节点+边+属性槽位定义）跨项目/平台不变；项目实例填充槽位值
- **树是演进式的**：不一次性固定；"创建树"和"更新树"是两个独立能力，做成独立模块
- **运行时无 LLM**：Schema 层离线 LLM 候选 + 人审；实例层确定性规则；查询理解层 LLM 只出候选、代码裁决

## 2. 节点定义："点"（✅ 已确认 2026-08-04）

**本体树的节点 = OBC/DCDC 所有需要人去确定和开发的"点"**。每个"点"包含属性、参数等方方面面，覆盖产品/结构/软件/测试/质量/工艺/项目所有需要确定开发的内容。

```
点（Node）= 需要确定/开发的决策单元
├─ 类型：参数 / 约束 / 功能 / 保护 / 故障 / 信号 / 状态机 /
│        设计决策（拓扑、器件选型）/ 试验条件 / 工艺参数 / 标准条款…
├─ 属性槽位：该点的"方方面面"（如输入电压范围点：min/max/unit/允差/
│            检测精度/条件/ASIL/验证方法/验证标准）
├─ 状态：未确定 / 已确定 / 变更中 / 已废弃     ← 项目实例层
├─ 责任角色：谁负责确定（电子代表/结构代表…）    ← 连接工程实体
├─ 依据：客户需求 / 标准条款 / 平台经验           ← 连接需求/标准/证据
└─ 值：项目实例挂载的值（本体相同、属性随项目变）
```

推论：
- 产品需求类（10 类实体）是"点"的类型体系
- 需求条目是"点"的实例（带值、带证据）
- 工程实体的活动产出"点"（活动要确定的内容）
- 关系是"点与点"之间的连接
- 一棵"点"的树 = 开发决策点的完整清单

## 3. 树的结构（两维度矩阵）❓讨论中

本体树 = **产品需求树 × 工程实体树**：

- **产品需求树**（产品是什么）：OBC/DCDC 根本体 → 12 域（产品概况/架构/功能/性能参数/保护/电气安全/通信诊断/环境/EMC/可靠性/标准合规/试验验证）→ 单参数节点（如"输出纹波因数"[number; %; ≤5%]）
- **工程实体树**（怎么开发）：学科（电子/结构/磁件/软件/测试/质量/工艺/采购/功能安全/EMC/包装/项目）→ 活动树（按阶段演进）→ 交付物
- **交叉关系**：产品节点 ↔ 工程节点（designed_by 电子 / verified_by 测试 / manufactured_by 工艺 / governed_by 质量）

树形参考：OBC 分级树见本目录 `obc_dcdc_tree_v1_draft.md`（待建），骨架基于 GB/T 40432-2021（OBC 母本）章节 + 行业惯例；工程实体树基于 `knowledge_base/raw/项目计划模板.xlsx`（1044 行 WBS，8 阶段 × 30 角色 × 交付物）。

## 4. 存储与演进（创建树/更新树）❓讨论中

- **单一事实来源**：版本化 JSON（git 可 diff/回滚，人审工作流友好）= DomainPack 内容升级（节点=object_types+terminology，边=relation_types 注册表+parent is-a，属性槽位=properties 升级）
- **运行时**：定稿后物化 SQLite（节点/边/属性槽位表），供遍历与文档落位
- **创建树**：LLM 从 16 份文档+行业知识提取候选（顶层约束 prompt）→ 候选 JSON+证据映射 → 人审 → 定稿 v1.0
- **更新树**：新文档/落位未覆盖反馈触发 → LLM 增量候选 → diff → 人审 → 发布 v1.1

## 5. 查询处理流程（8 类实体路由）❓讨论中

```
问题 → ①理解（意图+实体+项目上下文）
     → ②路由（按实体类分流：产品/工程/项目/物料/质量/供应商/文档/版本）
     → ③结构化检索（对象节点→属性槽位值：先项目实例值，无则通用值+注明；
                     证据通道挂证据链；版本通道取最新有效值）
     → ④组装判定（ContextPack + evidence_judge：sufficient/partial/insufficient）
     → 输出（结构化答案+证据+未覆盖提示）
```

## 6. 查询理解架构 ✅ 已确认（LLM + 规则混合）

讨论确认结论：规则用于"约束输出空间"（白名单）由代码强制，LLM 只出候选；决策逻辑（路由/兜底/裁决）留在代码侧。理由：LLM 概率性导致评测失真、未覆盖时猜而非报错、长 prompt 规则遵守率衰减、模型漂移；代码规则可测可审计。基于"LLM 出候选 + 代码裁决"原则：

```
确定性层（默认主路径）   规则+术语表+本体树枚举 → 意图/实体/槽位
                        快、稳、可复现、可审计、树更新即生效
LLM 语义层（可选 adapter） LLM 出候选（宽）：{意图top-3, 实体候选, 槽位} + 置信度
代码裁决层（强制）        白名单校验（节点存在性/术语表/项目实例）：
                        命中→用候选；未命中→回退确定性层；多候选→术语表精确裁决
离线提炼层（持续）        真实查询日志 → LLM 提炼新术语/规则 → 人审 → 并入确定性层
```

**关键约束**：白名单校验在代码侧强制（不是 prompt 建议）；LLM 层开启时评测可关闭（保证 Hit@K/MRR 可复现）；"未覆盖时猜而非报错"由代码层拦截（规则未命中 → not found，LLM 不得外推）。

## 7. 与 agent_kb_core 的对接 ❓讨论中

- DomainPack schema 升级：object_types 加 parent（轻量 is-a）；relation_types 升级注册表（name/category/inverse/undirected/source/target 类型）；properties 升级（值类型/单位/基数）
- 检索通道权重：graph ≥1.0（与 lexical 平级），vector 降为可选 provider；验证指标：结构化通道命中占比 ≥80%
- 输出：ContextPack 主输出 + 服务层可选 LLM 生成
- 属性值解析：确定性 parser（number/range/string/reference），结构化写入 Fact.payload / ObjectProjection.properties

1. **构建树 V1.0**：产品需求树（OBC+DCDC 分级）+ 工程实体树（模板驱动）→ 版本化 JSON
