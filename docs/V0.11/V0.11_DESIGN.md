# V0.11 Design — Knowledge Maintenance Proposal Layer

- Document ID: AKB-DD-V11-001 · Version: V1.0 · Status: DESIGN BASELINE（待评审）
- 基线：V0.10 FROZEN（52ce55c）· V0.10 design 6640ecf（frozen）· V0.9 FROZEN（88ea3bd）·
  V0.8 FROZEN（0e49c3d）
- 性质：DESIGN ONLY——零代码/零 migration 实施/零测试修改/零 frozen 触碰
- **主问题回答**：Fact → Reasoning → Evolution → Causal Projection → Health
  Governance → Persistence 之后，缺失的下一个语义抽象是——**治理闭环的
  "行动层"**：V0.9/V0.10 已让系统*看见*知识的问题（health 信号、conflict
  标注、causal 覆盖缺口），但发现的问题没有确定性的、可审计的、human-first
  的*行动通道*。Maintenance Proposal Layer 补齐"检测→提案→human 裁决"最后一环。

## 1. Capability Gap Analysis（V0.10 为什么不够）

V0.10 交付了稳定工程增强层（持久化/查询/快照）——它解决的是"看得更稳"，
不是"看得之后的行动"。缺口：

1. **发现-行动断裂**：akb_health_signals 与 akb_conflict_records 已持久化
   （migration 16/17 索引就绪），但没有任何对象把"一条 health 信号"转换为
   "一个可追踪、可裁决、可审计的 review 提案"——运维者面对信号表无法形成
   治理工作流；
2. **V0.9 设计的 MaintenanceTask 语义未落地**：V0.9 DESIGN §4 定义了
   MaintenanceTask（提案对象——system 只产提案，human 执行），V0.10 设计
   明示其"依赖 akb_health_signals 历史就绪"——该前置条件已满足（V0.10
   IMPL-002 落库+时序查询）；
3. **V0.8 task 通道已就绪但未复用**：VerificationTask 生命周期（created→
   running→completed/failed/cancelled）是现成的提案承载通道——缺的只是
   "从 health/conflict 信号自动生成提案"的确定性桥；
4. **counterfactual/机制比对的前置依赖未满足**：机制比对 level-2/3 需要
   ontology 术语冻结（未发生）；counterfactual 推理需要机制语义就绪——
   两者都被"治理行动层"阻塞：没有提案闭环，推理产物无处落地。

**结论**：下一层抽象是 Knowledge Maintenance Proposal Layer（Candidate C）——
它是唯一把 V0.9/V0.10 的检测面变成治理闭环的缺失环节，且全部前置依赖已就绪。

## 3. Architecture Boundary（数据流与禁止路径）

```text
akb_health_signals（V0.10 持久化）──┐
akb_conflict_records（V0.10）───────┤
                                    ↓ 确定性提案规则（同状态同提案集）
        ┌──────────────────────────────────────────┐
        │ V0.11 MaintenanceProposalRuntime（新增）  │
        │  proposal = V0.8 VerificationTask         │
        │  （task_type 新枚举 "maintenance_review"） │
        └──────────────┬───────────────────────────┘
                       ↓ graph:maintenance-proposal-create（审计）
        Governance（human）——V0.8 task 生命周期零修改：
        created → running → completed/failed/cancelled
                       ↓
        human 裁决产出（verdict/flag/退役）走既有通道——零新裁决路径

禁止路径（红线）：
- Proposal ↛ Knowledge mutation（提案零写 akb_assertions/kg_*/hypothesis 状态）；
- Proposal ↛ Auto execution（completed 语义 = human 已执行 review，非系统执行）；
- Proposal ↛ Truth selection（不得对 conflict 做裁决性标注变更）；
- ProposalRuntime ↛ Runtime behavior mutation（V0.8 task 生命周期零修改——
  仅新增 task_type 枚举值，经 V0.10 已确立的"枚举扩展"先例）。
```

## 4. Ownership Boundary

| Owner | 拥有 | 禁止 |
|---|---|---|
| MaintenanceProposalRuntime（V0.11） | 信号→提案的确定性转换；提案审计；提案查询面 | 执行提案；修改知识；修改 V0.8 task 生命周期语义 |
| V0.8 VerificationTaskRuntime（frozen） | task 生命周期 | 被 V0.11 修改（task_type 枚举扩展经既有通道） |
| Governance（human） | 提案裁决/执行 | 委托给系统 |
| V0.9 health/conflict（frozen） | 信号产生 | 被 V0.11 修改 |

## 5. Contract（字段级——Runtime object/Identity/Provenance/Determinism）

```text
MaintenanceProposalRuntime（agent_kb/maintenance/——V0.11 新包）

create_proposal_from_signal(signal_ref, *, actor_id) -> VerificationTask
    input: akb_health_signals.signal_id（存在性校验 fail-close——
           E-V11-PROPOSAL-SIGNAL-NOT-FOUND）
    identity: proposal task_id = V0.8 verification_task_identity(
              hypothesis_id=signal.target_ref 对应 hypothesis 或派生锚,
              task_type="maintenance_review", spec=确定性规格文本,
              evidence_requirements=(signal_id,))——复用 V0.8 算法零新 identity
    确定性: 同信号 → 同提案（幂等——重复创建零重复审计）
    provenance: graph:maintenance-proposal-create（proposal_id/signal_ref/
               task_id/actor）

create_proposal_from_conflict(conflict_id, *, actor_id) -> VerificationTask
    input: akb_conflict_records.conflict_id（同上校验）
    红线: 提案 spec 不得含裁决性结论（"请 review 该冲突"而非"该冲突已成立"）

list_proposals(*, signal_ref=None, cursor=None, limit=100) -> 分页面
    —— V0.10 ScaleQueryRuntime 模式复用（keyset cursor + PAGE-INVALID guard）

Determinism: 提案生成规则纯函数（同库状态 → 同提案集）；零 timestamp/random
    入 identity；canonical ordering（entry/ref 排序）。
```

## 6. Migration Analysis

**migration 18: NOT REQUIRED**——提案即 V0.8 VerificationTask（生命周期与
审计全部既有），信号源在 akb_health_signals/akb_conflict_records（V0.10 已
持久化），proposal 查询走 V0.8 task provenance 重放 + V0.10 query 模式。
**触发条件记录**：①提案需要独立于 task 的专属持久面 ②提案-信号关联需要
大规模反向索引（当前 provenance metadata 关联即可）。

## 9. P0/P1/P2

### P0（触发即 STOP）
- 提案自动执行（completed 语义被系统触发）；
- 提案写 akb_assertions/kg_*/hypothesis 状态；
- V0.8 task 生命周期语义被修改（非枚举扩展）；
- conflict 裁决性标注被提案自动变更。

### P1（实现期必须解决）
- signal.target_ref → hypothesis 的解析语义（entity 型信号无直接 hypothesis——
  需确定性派生锚规则，设计默认：entity 型走 created_from 锚）；
- proposal spec 文本的确定性生成（同信号同文本——禁止自由文本模板漂移）。

### P2（accepted 候选）
- 提案优先级排序视图（severity/score 加权）；
- 提案-裁决关联分析（analytics 前身）；
- 批量提案生成（同快照多信号一键提案集）。
