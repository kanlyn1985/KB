# V0.10 Design — Performance & Scale Engineering + Causal Reasoning Boundary

- Document ID: AKB-DD-V10-001 · Version: V1.0 · Status: DESIGN BASELINE（待评审）
- 基线：V0.9 FROZEN（88ea3bd）· V0.9 design dc15ec5（frozen）· V0.8 FROZEN（0e49c3d）·
  V0.7 FROZEN（3df1811）· V0.6 FROZEN（b317c6e）· V0.5 FROZEN（e7a286e）
- 性质：DESIGN ONLY——零代码/零 migration 实施/零测试修改/零 frozen 触碰
- **本设计的核心判断**："能力升级"与"工程优化"是否应合并为一个阶段？

## 1. 合并判断（任务书点题）

**裁定：部分合并——工程优化为主体（P1/P2 清偿），因果推理只进"边界与接口"
设计（能力预留），不实现推理运行时。**

理由：
1. V0.9 的 P1/P2 全部是**既存能力的规模瓶颈**（因果边基数/健康历史/冲突历史/
   provenance 扫描/registry 内存态），不是新能力——它们阻塞的是 V0.9 能力在
   生产基数下的可用性，价值独立且明确；
2. 因果推理/counterfactual（高级因果能力）依赖**机制语义比对**这一未冻结的
   难题（V0.9 P1-03：文本语义比对 DEFERRED）——在 scale 问题未解决前做推理
   扩张是给慢的系统加更多计算；
3. 因此 V0.10 = **Performance & Scale Engineering**（migration 16 + 索引 +
   分页 + 跨进程 registry），因果推理输出**边界契约**（counterfactual 入口、
   机制比对的分级策略）供 V0.11+ 消费——能力预留不预建。

| # | 缺口 | 性质 | 严重度 | V0.10 裁定 |
|---|---|---|---|---|

| 2 | health historical trend（无历史消费面） | 工程优化 | P1 | **SELECTED**——migration 16 akb_health_signals 落库 + 时序查询 |

| 4 | provenance-only 全表扫描（V0.8 遗产） | 工程优化 | P1 | **SELECTED**——索引+分页（不迁移历史数据，查询面加 INDEX 优化 + LIMIT/OFFSET contract） |

## 3. Migration 16 裁定（触发条件全部满足——设计期明示）

V0.9 FINAL 记录的三个触发条件在 V0.10 设计期全部成立：
①历史趋势查询——health signal 时序对比被明确列为 V0.9 P1-02 缓解路径；
②大规模索引需求——causal edge 基数 10^3-10^4 下内存投影不可持续（P1-01）；
③跨进程分析——registry 跨进程一致性需要持久锚。

**migration 16（版本 16，append-only，三新表）**：
- `akb_causal_edges`（causal_edge_id PK/cause_ref/effect_ref/relation_type/
  condition_refs_json/mechanism_ref/assertion_id/status/confidence/
  provenance_ref/fingerprint——索引：effect_ref/cause_ref/fingerprint）；
- `akb_health_signals`（signal_id PK/target_ref/target_type/signal_type/value/
  detail/health_id/provenance_ref/computed_snapshot——索引：target/type/snapshot）；
- `akb_conflict_records`（conflict_id PK/conflict_type/source_refs_json/
  target_refs_json/severity/status/fingerprint/snapshot——索引：type/status）；
- 边界：零修改既有表；rollback = drop 三表（全部可从 assertions/provenance
  全量重建——零数据损失）；降级路径保留（基数小于阈值时可退回内存模型）。

## 4. 与 V0.9 frozen architecture 的关系

```text
V0.9 frozen 三 runtime（causal/health/conflict）——只读面冻结为接口
V0.10 = 同三 runtime 的**持久化与查询增强层**（零语义变更）：
  CausalProjection.project() → 同 fingerprint，写 akb_causal_edges（替代内存）
  KnowledgeHealth.create_health() → 同 health_id，写 akb_health_signals
  ConflictRuntime.detect() → 同 conflict_id，写 akb_conflict_records
原则：**API 面零破坏**（现有 30 项 V0.9 测试必须零修改通过——行为锚）；
确定性零变更（同一 identity 算法——只是存储介质从内存/provenance 扩展到表）。
```

## 5. Determinism / Provenance / Governance 影响分析

- **Determinism**：identity 算法零修改（同输入同 id——表只是持久化介质）；
  查询面分页必须 canonical 排序（ORDER BY id + LIMIT/OFFSET——零 runtime
  ordering）；
- **Provenance**：三活动命名空间不变；新增 graph:registry-snapshot（registry
  序列化审计）；migration 16 本身记录于设计/实现 notes（schema 变更审计走
  版本控制而非 akb_provenance——沿用项目先例）；
- **Governance**：human-only 全延续——持久化不含任何自动裁决/自动修改；
  counterfactual 边界契约重申 hypothesis 专属。

## 6. 范围划定

- **V0.10 进入**：migration 16 三新表（append-only）、三 runtime 持久化接入
  （API 零破坏）、索引+分页查询 contract、registry 快照序列化、counterfactual/
  机制比对**边界契约**（仅设计）；
- **V0.11+**：机制语义比对 level-2（需 ontology 冻结）、MaintenanceTask 执行层、
  counterfactual 推理运行时、knowledge analytics；
- **永久禁止**：multi-agent autonomous、learning 自动改规则、LLM truth source、
  CausalProjection 直写 kg_*、system 自动执行 maintenance、自动 conflict resolution。
